# Sezi Server

The ready-made package for running your own server for **Sezi** — end-to-end encrypted, outward-closed group messaging and application platform. The server is a **blind relay**: it **cannot read** message content, media or plugin data. It queues and moves encrypted bytes, nothing more. The keys stay on the devices.

[![Deploy to Cloudflare](https://deploy.workers.cloudflare.com/button)](https://deploy.workers.cloudflare.com/?url=https://github.com/hasantr/sezi-server)

## Install (five minutes, no command line)

1. **Create a Cloudflare account** (free): <https://dash.cloudflare.com/sign-up>
2. Press **Deploy to Cloudflare** above. Cloudflare copies this repository into your own GitHub account, creates the database (D1) and the rate-limit store (KV, the brute-force brake) for you, and deploys.
3. When the deploy finishes you get an address: `https://sezi-server.<your-account>.workers.dev`
4. **In the Sezi app**, under "Add a server → Set up your own", paste that address. **The first account to register becomes the server's owner** — invitations, limits, everything, managed from the app.

That is all. The signing keys are generated by the server on its first boot; the database schema installs itself on the first request. No `wrangler secret`, no migration command. No card details.

> **Lite install:** this template installs "light" — messaging, groups and calls work in full; for **photo and file sharing** you enable R2 storage in Cloudflare afterwards (it asks for card verification; free up to 10 GB, a small fee beyond). How: enable R2 in the dashboard → create a bucket named `sezi-media` → Worker → Settings → **Bindings → add R2** (`MEDIA` / `sezi-media`). No code, no commands; the app shows the feature by itself.
> Running it on your own machine with `wrangler dev`? Then no R2 subscription is needed at all: uncomment the `[[r2_buckets]]` block in `wrangler.toml` and media is stored on the local disk.

## What you get

- 🔒 **A blind relay** — content is E2E encrypted; the server sees only sizes and counts
- 👑 **Owner administration from the app** — invitations, members, retention, storage limits, the usage panel
- 📊 **Usage panel** — storage / calls (TURN) / daily and monthly volume; optionally a "matches your bill exactly" mode with a CF API token (which you also enter from the app)
- 💸 **Budget guards** — a monthly TURN ceiling plus owner-set storage quotas: no surprise invoice on the free tier
- 📱 Multi-device, groups (Megolm), voice and video calls (LAN/STUN; CF TURN if you want it), a plugin platform
- 🧲 **Pluggable storage** — keep media in YOUR OWN store instead of, or alongside, R2 (see below)

## 🧲 Pluggable storage: your own cloud, or your own disk

The media store is not limited to R2. You can attach **any S3-compatible store** to the server
from the app — no code, no commands, no redeploy:

- **Cloud:** Backblaze B2, Wasabi, iDrive e2, MinIO in the cloud, another R2 account…
- **Your own disk (self-host):** a [MinIO](https://min.io) running on the same machine
  (e.g. a Raspberry Pi with a big HDD) → `http://localhost:9000`

**How:** in the app, as owner → Server → panel → the **STORAGE** section → add a store
(endpoint / region / bucket / access keys) → **Test**. That is it; new media is written there
from then on. The same place **drains** a store (blobs are moved off it) and **removes** it;
health and fullness are shown there too.

**A note on privacy:** media blobs are written end-to-end encrypted — whichever provider you
attach (Backblaze, MinIO, anyone) sees only **encrypted rubbish**. The keys never leave the
devices.

## Alternative: install from the command line

```bash
git clone https://github.com/hasantr/sezi-server && cd sezi-server
npx wrangler login
npx wrangler d1 create sezi          # put the database_id from the output into wrangler.toml
npx wrangler kv namespace create RATE_LIMIT   # put the id from the output into wrangler.toml
npx wrangler deploy
```

The `build/` directory contains compiled WASM — **you do not need to install Rust**. To build it
yourself from source: `cargo install worker-build && worker-build --release`.

## Running it on your own machine or VPS (without Cloudflare, advanced)

You can run the server around the clock **on your own VPS or device (Raspberry Pi / mini-PC)** without touching Cloudflare at all. This keeps `wrangler dev`'s local workerd alive under systemd and exposes it either through a cloudflared tunnel or a caddy TLS reverse proxy.

> ⚠️ **Security-critical:** in a self-managed install the relay must listen on **`127.0.0.1` only**; outside access must come **solely** through the tunnel or the TLS proxy. `--ip 0.0.0.0` puts the server on the internet as plain HTTP — **do not**.

A ready hardening kit (an EXACT wrangler pin, localhost binding, a WS shim, atomic backup, a healthz watchdog, ufw) is walked through step by step in [`deploy/`](deploy/) → **[deploy/README.md](deploy/README.md)**. Self-hosting uses its own config (`wrangler.selfhost.toml`, with the rate-limit KV enabled); the "Deploy to Cloudflare" button is unaffected by it.

## Optional configuration

| What | How | What happens without it |
|---|---|---|
| Your own signing key | `wrangler secret put JWT_SIGNING_KEY` (Ed25519 PKCS8 PEM) | Generated automatically on first boot (stored in D1) |
| TURN relay for voice and video | CF Realtime → TURN key → `TURN_KEY_ID` + `TURN_API_TOKEN` secrets | Calls work over LAN/STUN (enough on most networks) |
| Android push | Nothing — it works out of the box through the shared push relay. Read [Push notifications](#push-notifications-android-what-you-can-and-cannot-do) before changing it | — |
| Usage report matching the bill | From the app: Server → Usage → CF Analytics → enter a token | The server reports its own counters |
| Your own address for the Sezi web app | The variable `SEZI_WEB_ORIGINS` = the page's origin, e.g. `https://chat.example.org` (comma-separated for several) | Joining through a browser works from the official web app (`https://sezi-web.pages.dev`) and from a page on the server's own machine only; the invite door answers no other site |

## The door: what guessing an invite code costs

An invite code is short enough to read off a projector (39 bits), so the server bounds guessing
rather than relying on the code alone. Every request that asks about an invite — joining
(`POST /auth/redeem`), the invite page (`GET /<CODE>`) and the app's `POST /invites/describe` —
first takes one "miss" from its sender's budget, and a real invite gives it back:

- **30 misses per 5 minutes per sender**: an IPv4 address, or an IPv6 /64 (one device owns a
  whole /64, so a budget per IPv6 address would be none at all).
- **120 misses per 5 minutes per IPv6 /48** on top, across all its /64s.
- **No server-wide limit**, on purpose: it would let one person lock every joiner out.
- **Cost:** each guess is **one D1 row write** (the counter), plus one more on a hit. On the
  Workers free plan's 100,000 writes a day, a determined guesser spends your write budget before
  they find a code; watch Usage if joining suddenly slows. Finished windows are swept daily.
- The counter lives in D1 and **fails closed**: if D1 cannot be written, joining pauses for a
  minute.
- The door answers browsers only from the web app's origins (`SEZI_WEB_ORIGINS` above): its
  `POST`s must be sent as JSON (415 otherwise) and a browser's cross-site request from any other
  page is refused (403). The invite page answers a used or unknown code with the same status
  (200) as a good one, so another site cannot test codes through its visitors' browsers.

## Push notifications (Android): what you can and cannot do

A push from your server is only a **doorbell**: a contentless `{"type":"wake"}` that tells a
sleeping phone to connect and fetch what is waiting. Messages never travel inside it, so no
choice below exposes message content to anyone.

**How it works, and why the choices are narrow.** Firebase Cloud Messaging ties every device's
push token to ONE Firebase project — the one the app was built with. The Sezi app you install
from us is built with our project (`sezi-481e9`). Only a sender holding that project's
service-account key can wake those phones, and that key cannot be handed out (Google revokes a
published key). So the key lives in one small worker of ours, the **shared push relay**, and
your server asks it to ring the doorbell: it sends the relay the device's opaque push token,
nothing else.

**What you can do:**

- **Leave it as it is (the default).** Your server uses the shared relay with no setup. The relay
  sees a push token, the time, and your server's address — never who is messaging whom, and no
  content. In the app's server settings this shows as "Using the shared relay".
- **Turn push off.** Set the variable `PUSH_RELAY_URL` to `off` (Cloudflare dashboard → your
  Worker → Settings → Variables, or `[vars]` in `wrangler.toml`). Nothing leaves your server for
  push; messages arrive whenever the app is open or connected, and a phone left asleep catches up
  when it next opens the app. Each member can still choose the app's always-on connection (its
  settings, background delivery): the phone stays connected without push, at the cost of an
  ongoing notification and some battery. It is also what a phone without Google services uses
  anyway.
- **Use your own Firebase project — only with your own build of the app.** If you build and hand
  out your own Sezi app, with your project's `google-services.json`, to EVERY member, then set
  your project's id and service-account key on the server (in the app: Server → Settings →
  Notifications, or `FCM_PROJECT_ID` plus the secret `FCM_SERVICE_ACCOUNT`). Your server then
  talks to Google directly; the shared relay sees only the tokens of phones running our app
  (below), never your own build's.
- **Mix the two.** With your own project set, the server decides PER DEVICE. A device whose token
  Google refuses for your project (`SENDER_ID_MISMATCH` — it runs our app) gets that wake resent
  through the shared relay, and from then on all its wakes go there, until the device registers a
  different token. Every other device keeps going to Google directly through your project, in
  whatever order the wakes happen. The Notifications settings count the devices the shared relay
  wakes ("2 devices run the published app…").

**What you cannot do:**

- **Use your own Firebase project with the app from us alone.** Google refuses every wake to a
  device whose token belongs to another project. If you enter one while all your members use our
  app, every device ends up woken through the shared relay (as above) and your project serves
  nobody: the Notifications settings then say "Not usable with the published app" instead of "Set
  up". Press **Clear** there to remove the values. Saving new values (or clearing) makes the server
  ask Google about every device again on its next wake. If you have also switched the relay `off`,
  there is nothing to fall back to and our app's phones are not woken while asleep.
- **Run your own copy of the push relay** for our app: it would need our project's key, which is
  never distributed.
- **iOS:** there is no iOS app yet, so nothing here applies to iPhones.

## Updating

The **Deploy to Cloudflare** button does not fork this repository: it makes a **copy** in your
GitHub account — a new repository with one "Initial commit" and no history in common with this
one. GitHub therefore shows no **Sync fork** button for it, and a plain `git pull` from here
refuses ("unrelated histories"). Your copy also holds a few values this repository does not —
chosen or created when you deployed, and written into its `wrangler.toml`: the Worker's `name`,
your D1 database's `database_name` and `database_id`, and your KV store's `id`. An update must
keep exactly those and take **everything else** from here, `wrangler.toml` included: new
bindings, variables, Durable Object migrations and the compatibility date arrive that way, and
a server left on its old `wrangler.toml` breaks on the first update that needs one of them.

`scripts/update-from-upstream.sh` does that. You need a computer with `git` and `bash` (Linux,
macOS, or Git Bash on Windows), signed in to GitHub. Replace `<you>/<your-copy>` with your
copy's address (GitHub → your repositories; it is usually called `sezi-server`):

```bash
git clone https://github.com/<you>/<your-copy>.git sezi-update && cd sezi-update
git remote add upstream https://github.com/hasantr/sezi-server.git
git fetch upstream
git show upstream/main:scripts/update-from-upstream.sh | bash
git push
```

The script merges this repository into your copy (the first time it joins the two histories),
rebuilds `wrangler.toml` as this repository's file with your four values put back, checks that
nothing else differs, and commits; it changes nothing if the merge conflicts anywhere else. It
prints the values it kept — read them before you push. A file this repository deleted before
your first update stays in your copy; it is unused and harmless. For every later update run the
same lines again (in the same folder, skip the `clone` and `remote add`).

If your copy is old enough to have no `RATE_LIMIT` KV store, the script says so: create one
(dashboard → Storage & Databases → KV → Create), put its id on the `id = ` line under
`[[kv_namespaces]]` in `wrangler.toml`, commit, then push.

**The push redeploys your server** (Cloudflare Workers Builds builds every push to your copy's
main branch); watch it under Workers & Pages → your server → **Deployments**. If no deployment
starts, press **Retry/Deploy** there, or run `npx wrangler deploy` inside the folder above. In the
Sezi app, the server's update section says "Up to date" once the new version is live.

The database schema updates itself (self-migration) — no data is lost, and nobody has to join
again.

**Installed with `git clone` instead** (the command-line or own-machine paths below): your folder
already shares this repository's history, so `git pull` inside it is the whole update; then
`npx wrangler deploy`, or restart the service on your own machine
(`sudo systemctl restart sezi-relay`).

## More than one server in the same account

Watch out for a **database name collision**. When you install a second server into the same Cloudflare account, make the **D1 database name** unique on the setup screen (e.g. `sezi-family`, `sezi-school`). If you reuse the same name the two servers **share one database** and their members and data mix together. Different Worker and KV names are harmless. Note that free-plan quotas (requests, storage) are shared across every server in the account.

## Removing an installation

Deleting the Worker does **not** delete the database. D1 is an account-level resource that the
Worker merely binds, so deploying again under the same name hands the new Worker the old
database — the previous owner, members and signing key all come back. A clean start needs the
database gone too. In full, what a deploy creates:

| Name | What it is |
|---|---|
| `sezi-server` | The Worker. Deleting it stops everything and takes the user inboxes with it. |
| `sezi` | The D1 database. **The one people forget.** |
| `RATE_LIMIT` | The KV namespace. Harmless to leave. |
| `sezi-media` | The R2 bucket, only if you enabled media. Cloudflare will not delete it until it is empty. |

The GitHub repository the deploy created in your account stays until you remove it there.

⚠️ Do not simply abandon a server. While nobody has registered on it, the first person who learns
its address becomes its owner — that is how the very first account is created, and it stays open
until somebody takes it.

## Architecture (briefly)

Rust → WASM Cloudflare Worker. D1 (SQLite) for metadata and the queue, R2 for encrypted media, a per-user Durable Object inbox (WebSocket). Content is end-to-end encrypted with vodozemac (Olm/Megolm) — the server cannot read it, by design.
